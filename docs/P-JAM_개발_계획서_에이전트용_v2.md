- 작성일: 2026-11-14 (개정 2판: 2026-11-14 밤. 바뀐 내용은 14장)

- **프로토타입 기한: 2026-11-15** (4.1 M-P). 공모전 접수 마감이 11-15 23:59이고, 저장소·APK는 접수 시 참고자료(선택, 가산점)다.

## 0. 이 문서를 받은 에이전트가 할 일

1. 기획서와 이 문서를 모두 읽는다. 이어받은 세션이면 `docs/PROGRESS.md`부터 읽는다.
2. 10장에서 아직 답이 없는 질문(Q4·Q5·Q7·Q8)만 한 번에 묻는다. 답을 기다리지 않고 기본값으로 바로 시작하고, 답이 오면 반영한다. "답변 완료" 항목은 다시 묻지 않는다.
3. **M-P(4.1)를 먼저 한다.** 11/15 안에 동작하는 프로토타입을 만든다.
4. 11/16부터 M0(4.2, 0단계 검증)을 수행하고 `docs/FINDINGS.md`를 채운다.
5. M0 결과로 이 계획서가 바뀌어야 하는 부분(매핑, 권한, 오디오 방식)을 `docs/PLAN_CHANGES.md`에 적고 사용자에게 알린다. **확인을 기다리지 않고 적은 대로 진행한다.** 사용자가 다르게 정하면 그때 바꾼다.
6. M1부터 순서대로 구현한다. 각 작업은 "완료 확인" 항목을 통과해야 끝난 것이다.
7. 작업을 끝낼 때마다 `docs/PROGRESS.md`를 갱신한다 (2장 9번).

기획서 10장의 "계획서에 대한 확인을 받은 뒤 구현을 시작한다"는 이 문서로 확인이 끝난 것으로 본다. 다시 확인을 구하지 않는다.

**수동 확인 표시:** Virtual Console은 에뮬레이터가 띄우는 **웹 페이지**다(1.3). 에이전트는 먼저 T0-0으로 이 페이지를 직접 조작할 수 있는지 확인하고, 되면 `[수동]` 항목 가운데 "Virtual Console 조작 → logcat·화면으로 결과 확인"으로 끝나는 것은 스스로 돌린다. 귀로 들어야 하는 것, 화면 녹화, 시연 리허설은 그대로 사용자 몫이다. 직접 조작이 안 될 때는 `[수동]`이 붙은 항목은 에이전트가 절차를 `docs/DEMO.md` 또는 FINDINGS에 적어 사용자에게 실행을 요청하고, 사용자가 알려 준 결과(또는 logcat 출력)를 기록한다. `[자동]`은 에이전트가 명령으로 직접 확인한다.

### 1.3 공식 문서에서 추가로 확인한 것 (2026-11-14 밤)

출처: 차량 에뮬레이터 사용 문서, Virtual Console 사용 가이드, Connect SDK 개요 (주소는 이 절 끝). **Virtual Console에 카드가 있다는 것은 값을 바꿀 수 있다는 뜻일 뿐, 앱이 Vehicle SDK로 그 값을 읽을 수 있다는 보장은 아니다.** 읽히는지는 T0-3(V2)에서 확인한다.

**접속 방법**

```bash
adb forward tcp:8088 tcp:8088
# 그다음 PC 브라우저에서 http://127.0.0.1:8088/ → Emulation Controls
```

- Pleos Connect Emulator **v2.1.0 이상**에서만 된다. 안 열리면 에뮬레이터 실행 여부 → 이미지 버전 → `adb devices` → 포워딩 재실행 → PC의 8088 포트 점유 순으로 확인한다.
- 문서에는 명령줄·API로 조작하는 방법이 없다. 화면 조작만 설명한다. 다만 웹 페이지이므로 브라우저 자동화가 가능할 수 있다(T0-0).

**이 앱이 쓰는 카드와 값** (Domain → 카드)

| 용도 | 카드 | 값 | 계획에 미치는 영향 |
|---|---|---|---|
| 기어 | Motion → Gear Selection | P, R, N, D | 콘솔에서 기어를 바꿀 수 있다. 앱이 읽는 방법(3.6)만 확인하면 된다 |
| 브레이크 | Motion → Brake Pedal | 0~100% | 밟음/뗌이 아니라 **비율**이다. SDK가 주는 값이 불리언인지 수치인지 P7·T0-5에서 확인 (3.4) |

- Climate에 HVAC Power(Off/On) 카드가 따로 있다. 전원이 꺼져 있으면 다른 공조 값이 안 바뀌거나 함께 바뀔 수 있으므로, 검증과 시연 전에 **HVAC Power를 On**으로 둔다. HVAC Dual(운전석·동승석 동기화)은 Off로 둔다.

**권한 (Connect SDK 개요)**

- 출시 앱은 App Market과 협의·승인된 권한만 쓸 수 있고, 승인되지 않은 권한을 선언하면 심사에서 떨어진다. 공모전 단계에서는 매니페스트 선언만으로 호출된다(기획서 2.1). 그래도 **쓰지 않는 권한은 선언하지 않는다**(T4-4)는 원칙이 더 중요해진다.
- 공개 SDK는 Vehicle, NaviHelper, TextToSpeech, SpeechToText, FusedLocation 다섯 가지로 기획서 규칙 2와 같다.

## 2. 작업 원칙

1. **작업 단위 = 커밋 단위.** 5장의 작업 ID(T1-3 등)를 커밋 메시지 앞에 붙인다.
2. **완료의 정의:** 빌드 성공 + 해당 단위 테스트 통과 + 작업의 "완료 확인" 통과. `[수동]` 항목은 사용자 확인 전까지 "확인 대기"로 표시하고 다음 작업을 진행한다.
3. **매일 끝에** `./gradlew lintDebug testDebugUnitTest assembleDebug`가 통과하는 상태로 둔다.
4. **SDK 호출은 `PleosVehicleInputSource` 한 파일(또는 `input/pleos/` 패키지)에만** 둔다. 시그니처가 예상과 달라도 수정 범위가 그 안에서 끝나게 한다.
5. **추측 금지.** 시그니처를 모르면 IDE/`javap`/sources jar로 확인하고 FINDINGS V1 표에 적은 뒤 쓴다.
6. **발견 사항은 즉시 기록.** FINDINGS는 마지막에 몰아 쓰지 않는다.
7. 비밀값(서명 키, 키 비밀번호)은 저장소에 넣지 않는다. `.gitignore`에 `*.jks`, `*.keystore`, `keystore.properties`, `local.properties`를 넣는다.
8. 커밋 작성자 이름·이메일은 개발 PC의 현재 git 설정을 그대로 쓴다(10장 Q6). 에이전트는 이 설정을 바꾸지 않는다.
9. **`docs/PROGRESS.md`를 유지한다.** 새 세션은 이 파일부터 읽는다. 맨 위 "현재 상태"에 끝난 작업 ID, 확인 대기 중인 `[수동]` 항목, 다음 할 일, 막힌 것을 적는다. 최신 항목이 위에 온다.
10. **검증은 `scripts/check.sh` 한 번으로 돌린다** (13장). 새 `[자동]` 확인이 생기면 이 스크립트에 넣어, 이전 작업이 깨졌는지 매번 함께 확인한다.
11. **한 작업에서 60분 넘게 막히면** 대체 경로(기본값, 화면 조작 대체, 가짜 입력)로 넘어가고 PROGRESS의 "막힌 것"에 적는다.

## 3. 계획 단계 결정 (기획서가 열어 둔 부분을 정함)

M0 결과가 다르면 바꾸고 `docs/PLAN_CHANGES.md`에 남긴다.

### 3.1 프로젝트·빌드

| 항목 | 결정 |
|---|---|
| 도구 버전 | AGP 8.8.2, Kotlin 2.0.0, Compose BOM 2024.04.01 이상, JDK 17 (샘플과 동일) |
| SDK 레벨 | minSdk 28, targetSdk 34, compileSdk 34. SDK 2.3.x가 compileSdk 35를 요구하면 compileSdk만 35로 올린다 |
| Vehicle SDK | `ai.pleos.playground:Vehicle:2.3.2` (실패 시 2.3.1) |
| AAOS Car API | `android { useLibrary("android.car") }`. 매니페스트에 `android.hardware.type.automotive` uses-feature. distractionOptimized 메타데이터는 넣지 않는다. 시작 가이드의 Automotive 템플릿과 대조해 확인. `Car`·`CarPropertyManager`를 쓰는 코드는 `GearSource` 구현 한 곳에만 두고 `Throwable`까지 잡는다(Car 라이브러리가 없는 기기에서는 `NoClassDefFoundError`가 난다). 실패하면 3.6의 4단계로 동작한다 |

### 3.2 스레드·시간 모델

- SDK 콜백 스레드는 미확인(V1). 콜백 안에서는 **수신 시각(`elapsedRealtimeNanos`)만 찍고** 채널에 넣은 뒤 바로 반환한다.
- 엔진 상태(트랙·녹음·뮤트)는 **엔진 스레드 하나만** 바꾼다. UI와 입력은 명령 큐로 요청한다.
- UI에는 불변 스냅샷을 `StateFlow`로 내보낸다. 재생 위치는 스텝이 바뀔 때만 갱신한다.

### 3.3 녹음 흐름 세부

| 상황 | 동작 |
|---|---|
| 정지 상태에서 녹음 | 재생 시작 → 1마디 카운트인(메트로놈 4번) → 2마디 녹음 → 재생 상태 |
| 이미 루프가 도는 중 녹음 | 다음 루프 시작점에서 녹음 시작. 그 직전 1마디 동안 메트로놈. 남은 시간이 1마디보다 짧으면 한 바퀴 더 기다린다 |
| 녹음 시작 직전 입력 | 시작점보다 반 스텝 이내로 이른 입력은 스텝 0으로 기록 |
| 녹음 끝 직전 입력 | 스텝 32로 반올림되는 입력은 스텝 0으로 기록 (루프이므로) |

| 녹음 중 기어 이탈 | 녹음 취소, 그때까지 찍힌 내용 유지, 재생 정지 |

스텝 길이: 100 BPM에서 150ms, 140 BPM에서 약 107ms. 루프 한 바퀴는 100 BPM에서 4.8초다.

### 3.4 입력 판정 세부

- **변화 판정은 "콜백이 왔다"가 아니라 "값이 직전과 다르다"로 한다.** 구독 직후 현재 값이 한 번 들어오는 경우와 같은 값이 반복되는 경우를 걸러낸다. 기준값은 초기 `get…` 결과로 잡는다.
- 방향지시등: 꺼짐→좌, 꺼짐→우만 Trigger. 좌→우 직접 전환도 Trigger로 본다. 비상등 값이 있으면 무시한다 (V5로 확정). Virtual Console에는 방향마다 Blink와 Flash 두 값이 있다(1.3). 둘 다 그 방향으로 보고, 같은 방향 안에서 Blink↔Flash로 바뀌는 것은 Trigger가 아니다.
- 브레이크: SDK 값이 불리언이면 false→true가 Trigger다. 수치(비율)면 **5% 이상으로 올라가는 순간**이 Trigger이고 2% 아래로 내려가야 다시 받을 수 있다. 임계값은 T0-10 뒤에 조정한다.
- 핸들 3구간: 기본 경계 ±10°, 히스테리시스 ±3°, ±30° 밖은 가장자리 구간 유지. V4 결과로 조정한다.
- 온도 "한 단계"는 capability의 증분 단위(없으면 관측된 최소 변화량)로 정의한다.
- 풍량·창문은 capability의 min~max로 0.0~1.0 정규화한다. 범위를 못 받으면 Level 입력을 미지원 처리한다.
- **AUTO 연동 주의:** 실차에서는 AUTO를 누르면 A/C·풍량이 함께 바뀔 수 있다. 에뮬레이터에서는 값이 독립이므로 P0에서는 처리하지 않고, P1에서 "AUTO 변화 후 300ms 안에 온 A/C·풍량 변화는 무시" 옵션을 `InputMapper`에 넣는다. FINDINGS에 알려진 제약으로 적는다.

### 3.5 소리

- 샘플은 **저장소 안의 생성 스크립트로 직접 합성**한다(`tools/soundgen/`, 결과 WAV는 `assets/soundpacks/`에 커밋). 외부 샘플을 쓰지 않으므로 라이선스 문제가 없다. `LICENSES.md`에 "자체 합성, 생성 스크립트 경로"를 적는다.
- 형식: 44.1kHz 또는 48kHz(V8·기기 출력에 맞춤), 16bit mono WAV, 샘플당 1초 이내.
- **옥타브는 재생 속도로 만들지 않는다.** SoundPool의 rate는 0.5~2.0 범위라 옥타브(×2, ×0.5)에 조옮김(±3반음)을 더하면 범위를 넘는다. BASS는 음마다 3옥타브 샘플을 따로 만든다. 조옮김만 rate로 처리한다(2^(n/12), n=−3~+3 → 0.84~1.19).
- 재생기는 `Sampler` 인터페이스 뒤에 둔다. 1차 구현은 `SoundPoolSampler`, 대안은 `MixerSampler`(AudioTrack 스트림에 직접 믹싱). SoundPool은 "미리 예약" 재생이 안 되므로 스텝 시각에 맞춰 즉시 `play()`한다. 흔들림이 기준을 넘으면 6장 게이트 G2에서 교체한다.
- 오디오 포커스: `USAGE_MEDIA`, `AUDIOFOCUS_GAIN` 요청. 영구 손실 시 재생 정지, 일시 손실 시 일시정지 후 복귀 시 사용자가 다시 재생 (V8 문서와 다르면 문서를 따른다).

### 3.6 기어 판정 대체 순서 (V3 결과에 따라)

1. `CarPropertyManager` + `GEAR_SELECTION` 구독 (권한 `android.car.permission.CAR_POWERTRAIN`, 안 되면 `pleos.car.permission.CAR_POWERTRAIN`도 선언해 재시도)
2. `CURRENT_GEAR`
3. `CarUxRestrictions`만으로 판정 + 화면에 "기어 확인 불가" 표시
4. 모두 불가: P로 간주 + "기어 확인 불가" 표시 (기획서 4.1)

어느 단계로 동작하는지 "내 차 장비" 화면과 FINDINGS에 표시한다. 디버그 빌드에는 잠금을 강제로 켜는 버튼을 둔다(시연 리허설용).

### 3.7 BASS·MELODY 입력 확정안 (기획서 4.3 보완)

기획서 4.3 표에서 해석이 갈리는 부분을 아래로 정한다. Q5에 사용자 답이 없으면 이대로 만든다. T2-2에서 연주해 보고 어색하면 바꾸고 PLAN_CHANGES에 적는다.

**공통:** 방향지시등 입력도 브레이크와 같은 Trigger다. 모드를 바꾸는 입력이 아니라 **그 순간 소리가 난다.** 핸들 구간(Zone)은 소리를 내지 않고 "현재 음"만 바꾼다.

| 트랙 | 핸들 구간 | 브레이크 | 방향지시등 좌 | 방향지시등 우 | 화면 패드 |
|---|---|---|---|---|---|
| BASS | 현재 음 선택: 중앙=1도, 좌=4도, 우=5도. 시작값과 핸들 미지원 시 기본은 1도 | 현재 음을 가운데 옥타브로 연주 | 현재 음을 한 옥타브 아래로 연주 | 현재 음을 한 옥타브 위로 연주 | 3음 패드(가운데 옥타브) + 핸들 대체 3버튼은 현재 음 선택 |
| MELODY | 구간이 **바뀔 때** 커서를 옮긴다: 좌(낮음)=0번, 중앙(중간)=3번, 우(높음)=6번 | 커서 위치의 음 연주 | 커서를 한 칸 내린 뒤 그 음 연주 | 커서를 한 칸 올린 뒤 그 음 연주 | 8음 패드(누른 음 연주, 커서도 그 음으로 이동) |

- MELODY는 펜타토닉 8음을 낮은 음부터 0~7번으로 둔다. 커서 시작값은 3번이다. 커서는 0~7을 벗어나지 않는다(끝에서는 같은 음을 다시 연주).
- BASS 샘플은 3음 × 3옥타브 = 9개다(3.5, T1-4).
- 중앙을 1도로 둔 이유: 핸들을 놓은 기본 자세에서 으뜸음이 나야 처음 치는 사람도 어울리는 소리를 낸다.

## 13. 운영 방식 (가벼운 하네스)

계약 협상, 스프린트마다 승인 대기, 여러 역할이 번갈아 도는 방식은 쓰지 않는다. 이 문서의 "완료 확인" 열이 곧 합의된 검증 기준이다. 에이전트 하나가 구현하고 아래 세 가지만 유지한다.

### 13.1 `scripts/check.sh`

한 번 실행으로 지금까지의 `[자동]` 확인을 모두 돌린다. P1에서 만들고 작업마다 늘린다.

- 순서: `./gradlew lintDebug testDebugUnitTest assembleDebug` → (에뮬레이터가 연결돼 있으면) 설치 → 실행 → 스모크.
- 스모크: `adb shell am start`로 앱을 띄우고, `adb shell uiautomator dump`로 화면 노드를 뽑아 기대한 요소(예: 녹음 버튼의 contentDescription)가 있는지 본다. Compose 요소에 `contentDescription` 또는 `testTag`를 달아 둔다. 실행 후 `adb logcat -d`에서 이 앱의 `FATAL EXCEPTION`이 1건이라도 있으면 실패다.
- 에뮬레이터가 없으면 설치·스모크는 `SKIP` 한 줄을 찍고 넘어간다.
- T0-0이 성공하면 차량 조작 스모크를 추가한다: `scripts/vc.sh`로 브레이크·기어를 바꾸고 logcat(`PJAM_SIG`)에 해당 이벤트가 찍혔는지 확인한다. 시연 시나리오(8장)의 조작 순서를 그대로 스크립트로 만들어 두면 리허설 전 점검에 쓸 수 있다.
- 출력은 기준 하나당 한 줄(`PASS <이름>` / `FAIL <이름> → 로그 경로`). 하나라도 FAIL이면 0이 아닌 종료 코드. 상세 로그는 `build/check-artifacts/`에 두고 git에 올리지 않는다.
- T4-5의 개인정보 점검(실명·이메일 문자열 검색)도 이 스크립트에 넣는다. 찾을 문자열 목록은 저장소 밖 파일에서 읽고, 출력은 `파일 경로:줄 번호`만 한다.

### 13.2 `docs/PROGRESS.md`

2장 9번. 양식:

```markdown
# 진행 기록

## 현재 상태
- 끝난 작업:
- 확인 대기([수동]):
- 다음 할 일:
- 막힌 것 / 대체 경로로 넘어간 것:

## 기록 (최신이 위)
- 11/15 21:10 P6 완료. check.sh 통과. …
```

### 13.3 마일스톤 검수

M1·M2·M4가 끝날 때만, 구현 맥락이 없는 별도 에이전트(또는 새 세션)로 1회 검수한다. 협상이나 재검수 반복은 하지 않는다.

- 입력: 기획서 7.1 완료 조건, 이 문서의 해당 마일스톤 "완료 확인", `scripts/check.sh` 결과.
- 하는 일: check.sh 실행, 완료 확인 항목을 하나씩 대조, 깨진 것과 빠진 것을 `docs/REVIEW_M<n>.md`에 필수 수정 / 권장 수정으로 적는다.
- 필수 수정만 고친다. 권장 수정은 12장 축소 순서보다 뒤다.
- M-P에는 검수를 하지 않는다. 사용자의 `[수동]` 확인 1회로 대신한다.
